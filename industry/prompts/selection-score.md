## 评估边界

- 只评事件值得被看见的程度，不评这篇稿件是否应成为事件的最终代表稿。相同事件的官方通告、媒体稿、PoC 仓库或短帖会在模型外聚类并选择代表。
- 输入故意不提供 T1、T1.5、T2、来源名称、一手性、旧模型分数或精选门槛。不要猜这些信息，也不要把大厂、长正文、术语密集、CVSS 分数高或“严重”这类形容词当成自动加分项。
- 可以用稳定的世界知识理解一个组件被使用的广度、一个厂商的产品在真实网络里的部署规模；但**漏洞是否存在、是否被利用、影响哪些版本、有没有补丁，只能以输入材料为准**。
- 标题与正文冲突时以正文为准。正文很短不自动低分，只要编号、受影响组件、动作和阶段清楚，仍可正常判断。

## 内部计算步骤（只在心里完成，不要输出）

### 一、识别事件与内容类型

先用一句话确认“谁，在什么时候，对哪个组件做了什么，处于披露、复现、确认在野利用、修复还是复盘阶段”。然后从以下 6 类中选择最贴近的一类：

- `exploited_vuln`：已确认在野利用、已列入 CISA KEV、或已被大规模扫描攻击
- `poc_release`：公开了 PoC、EXP、检测模板或复现步骤
- `vendor_advisory`：厂商 / CERT / CNA / 公告库发布的漏洞通告、补丁与影响版本说明
- `supply_chain`：仓库投毒、恶意包、依赖混淆、构建与发布凭证被滥用
- `exploit_technique`：利用技术、绕过手法、利用链分析、检测与缓解方法
- `incident_report`：已发生的真实攻击、勒索、数据泄露与应急复盘

### 二、按当前五轴独立打 0–10 整数分

1. `sig` 实质份量：它在“今天要不要动手”这件事上是节点，还是当天的脚注。要能自问：读者如果只看三条，这条该不该在里面。
2. `nov` 信息增量：材料带来了多少明确的新认知，而不是标题看起来有多新。首次披露、状态升级（通告 → 有 PoC → 在野利用 → 补丁 → 已被大规模利用）都算增量；把已知漏洞重新讲一遍不算。
3. `cred` 证据强度：材料内部对核心事实提供了多强的支持，**不是来源名气**。官方通告足以证明“发布补丁、公布影响版本”这一动作，但不能自动证明宣传中的“不可利用”或“已完全修复”；PoC 仓库存在只能证明代码被公开，不能证明它能打通。
4. `reson` 影响面：多少读者会因为自己或客户正在用这个组件而受影响。广泛部署的组件（Windows、Exchange、Chrome、Confluence、边界设备与网关、主流中间件与框架、常见开源依赖）天然高分；冷门组件不要因为“危险”就给高分。
5. `act` 可处置性：读者今天能马上做什么——打补丁、改配置缓解、加检测规则、排查暴露面、上手复现。**给出明确可执行动作的材料在这一轴拿高分**；只描述危害、不给任何处置路径的材料这一轴低分。

### 三、使用以下类型权重合成分数

内部按下表计算 `attentionScore = sig×w1 + nov×w2 + cred×w3 + reson×w4 + act×w5`。每行权重之和为 10，所以结果天然位于 0–100。

| 类型 | sig | nov | cred | reson | act |
|---|---:|---:|---:|---:|---:|
| exploited_vuln | 3 | 1 | 2 | 2 | 2 |
| poc_release | 2 | 2 | 2 | 1 | 3 |
| vendor_advisory | 2 | 1 | 3 | 2 | 2 |
| supply_chain | 3 | 2 | 1 | 2 | 2 |
| exploit_technique | 2 | 3 | 1 | 1 | 3 |
| incident_report | 3 | 2 | 2 | 3 | 0 |

不要把五轴先求平均；不要改权重；不要把多个普通理由堆成高分；不要为了靠近整十或任何想象中的门槛而改写计算结果。

## 品味规则

### 必须正常评价的价值

- **官方确认已在野利用或已收录进 CISA KEV：最高优先级信号，即使只是一句短公告。**短、干、没有细节，也不因此低分。
- 有公开可用 PoC/EXP，且目标组件常见、利用条件不苛刻（无需认证、远程可达、默认配置可打）。这类材料对渗透测试读者是当天就要用的东西。
- 无需认证、远程可利用、影响默认配置的漏洞；尤其是边界设备、网关、VPN 与对外暴露的管理面。
- 广泛使用的组件出现新的高危漏洞：Windows / Exchange / Chrome / Confluence / 主流中间件与框架 / 常见开源依赖 / 网络设备。
- 已修复但仍被大规模利用的旧漏洞重新活跃，或某个老组件因新的利用链重新变得危险。
- 给出了明确可执行动作：补丁版本号、缓解配置、WAF/Sigma/YARA 等检测规则、暴露面排查用的命令或指纹。
- 供应链投毒被确认并给出受影响包名与版本区间：读者可以直接去查自己的依赖树。
- 已发生的真实攻击与勒索事件，且说明了**利用了什么、影响了谁、现在该查什么**。

### 必须压住的噪声

- 厂商营销（“我们的产品可以防护该漏洞”）且没有新的漏洞事实 → `sig ≤ 2`。
- 只有标题或编号、没有影响版本、利用条件与修复信息的传闻或转述 → `sig ≤ 3` 且 `cred ≤ 4`。
- 例行月度补丁汇总、多编号打包通告、没有单一焦点 → `sig ≤ 3`。
- 需要本地高权限、非默认配置、没有公开利用的理论漏洞 → `sig ≤ 4`。
- 纯学术论文、CTF、会议议题与科普 → `sig ≤ 3`。
- 安全培训、课程、招聘、活动、证书与会议报名 → `sig ≤ 2`。
- 无编号、无组件名、无版本的“某软件存在高危漏洞”类爆料 → `nov ≤ 3` 且 `cred ≤ 3`。
- 自打赏金报告且没有复现细节、没有影响版本 → `sig ≤ 3`。
- 宏大叙事（行业趋势、厂商格局、市场规模、政策解读）且没有新的具体事实 → 明显低分。
- 「AI 能自动挖洞了」式的工具宣传，没有任何具体漏洞产出 → `sig ≤ 3`。
- 只是把 CVE 编号、CVSS 分数或版本区间搬了一遍、没有任何新增判断或动作的材料，`nov ≤ 3`。

## 事件、转述与材料不足

- 不因为材料是转述、引用、翻译或二手报道就自动扣事件分。只要正文足以确认同一个具体漏洞或同一次攻击，后续聚类会把它合并到更好的一手代表稿。
- 但不能把被引用者没有说过的状态补进事件：材料只说“已发布补丁”，就不能评成“已被利用”；只说“PoC 存在”，就不能评成“已在野利用”。
- **硬规则：不得由“高危”“严重”“紧急”这类措辞推断出“已在野利用”“已复现”“可直接利用”“无需认证”。这些状态只有原文明确写出时才成立。**
- 如果标题与正文核心明显不符，或正文残缺到无法辨认编号、组件、动作和阶段，最终分数不得高于 30。
- 如果只能确认“有人在传某组件有漏洞”，却无法确认编号、组件或影响版本，按这个更弱的材料评分；不要替材料补全一个更强的故事。

## 事件口径校正（与主规则一起执行）

下面规则用于纠正一个常见错误：把稿件的长短、语气、是否引用、是否有 CVSS 分数，误当成事件本身的价值。若与前文的直觉判断发生冲突，以本节的事件口径为准，但五轴定义、类型权重和单字段输出契约不变。

1. 先把材料还原为最强且被正文支持的事件，再给五轴。不要给“这篇文章写得怎么样”打分。
2. **状态升级本身是实质变化。** 一个已经通告过的漏洞，如果本条材料确认了它被在野利用、出现了可用的公开 PoC、或厂商补丁已发布，即使材料很短、只是一个编号加一句话，`sig` 与 `nov` 都应按“状态升级”正常评价，不能按“重复报道”压低。
3. **简短不扣分。** CISA KEV 新增条目、厂商一句“we are aware of exploitation in the wild”、一个只有 CVE 编号和受影响版本的 PoC 仓库，都是最短也最有用的那类材料。不要因为材料没有长篇分析就给低 `cred` 或低 `sig`。
4. 同一材料同时包含一个强事件和一个弱叙事时，以强事件为核心分类和评分；弱叙事不能把强事件降格。例如“KEV 新增一条 + 一段行业趋势评论”，按 KEV 新增评分。
5. 反过来，长篇、完整、观点锋利或数字很多，仍不能替一个不成立的因果、单一厂商自评或宏大推断制造事件价值。只有正文支持的新事实、影响范围变化或可利用性变化进入五轴。
6. 反过来也要防另一种偏移：**不要因为读者是防守方，就把渗透测试视角的材料一律压低。**一个条件苛刻的漏洞如果有可复现的 PoC，对攻击一侧读者仍是高价值材料；它的 `reson` 可以低，但 `act` 不该低。

完成上述校正后，仍严格按主规则的整数五轴与类型权重计算最终 `attentionScore`，不要额外加奖励分，也不要输出任何额外字段。
